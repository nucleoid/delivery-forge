# Publication and uncertain-result recovery

Issue #10 implements a single-run fixture publication core and a separately configured GitHub CLI transport. The integrated candidate still awaits final validation/review. No live GitHub operation is configured or authorized by this source change. General production publication remains unavailable because the actual immutable-source preparer, ownership profile and live review integration are not configured.

The parent owns publication. A worker's mode, validated receipt bytes, journal import or caller observation never constructs production authority. The run token has an opaque issuer, immutable ceiling/revision, exact patch inputs and independently pinned review receiver. A later explicit higher grant creates a new reconciled revision referencing prior evidence and repeats current head/policy checks; it cannot edit the old ceiling. Resume does not escalate.

Before any external action, the core serializes repository/ref operations across service instances, reads fresh remote ref/PR facts, then refreshes local head/tree/full patch/artifacts/ownership/stop state and current accepted review. Required policy gates must have allowed exact-bound outcomes. Merge requires both independently issued and hosted review, exact CI and protected normal-merge checks. No release, deployment, squash, rebase, auto-merge or bypass operation is in the host interface. All read/action/journal/serialization waits have finite budgets. A timed-out action that ignores cancellation fences the ref until the task settles; the original result cannot turn into late success.

Each intent binds key, issuer-owned run/revision, action, repository/refs and base/head/tree. Record the send intent before invoking the host. After an uncertain response, inspect the remote result; an absent or ambiguous result remains unresolved and must not trigger automatic resend. Repeated keys cannot silently bind another revision/action. Readback-confirmed results produce append-only existing-v1 publication receipts. Receipt import is evidence only and cannot restore ephemeral authority after restart.

Fixture ports and their external-call ledger perform no network/operating-system publication. Fixture outcomes remain marked Fixture. The fixture service refuses a Production GitHub adapter even if a separate disposable grant exists. Parent-supplied journal ports hold append-only local evidence; no production persistent journal or recovery profile is certified. Imported journal/receipt data cannot reconstruct an opaque parent-issued run.

The GitHub transport defaults unavailable. Explicit read configuration pins absolute executable bytes, working directory, exact CLI version and finite timeouts; it probes existing authentication without changing it. Read APIs inspect source/target refs, exact PR ownership/head, applicable rules, protection and required checks; incomplete/truncated or unknown observations never become passing merge evidence. The real process executor concurrently captures bounded streams, cancels/kills/closes on failure, finite-drains and reports residual uncertainty. Synchronously blocking OS calls and the server check-to-action race remain limitations.

A completed executor result that reports residual process uncertainty leaves a process-wide repository/target-ref barrier across keys, grants and adapter instances. There is no reset API or settlement capability for that result; remote readback alone cannot remove the barrier or certify physical cleanup. An incomplete command can release its task barrier only after an owned completed result certifies no residual uncertainty. Faulted/cancelled command tasks retain the physical barrier. Process restart is not settlement proof: the parent must independently resolve physical and remote uncertainty before authorizing another process. Fully quiescent command failure remains ordinary uncertain-result recovery. Native cancellation is checked before configuration work and immediately before starting the process; cancellation racing after start still requires bounded cleanup.

Modern protected checks retain each required context and its App ID. A successful same-name check from another App or a legacy status cannot satisfy an App-specific requirement. Missing/invalid App identities and incomplete observations deny merge; explicit App ID `-1` permits any observed App, while legacy context-only requirements retain their legacy matching behavior. Observed check runs must belong to the exact source head and finish successfully.

For a legacy required context, a commit status and check run sharing that name must both pass when both are observed. A successful status cannot mask a failed, pending, cancelled, incomplete or wrong-head check. Status-only and check-only contexts remain valid when their observed evidence passes. This follows GitHub's [required-check troubleshooting contract](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks); local observation still cannot eliminate the server check-to-action race.

Applicable active rules are read with explicit 100-item pages, at most ten pages under the shared finite read deadline. A short final page proves collection completion; a full final page, truncated response or unsupported rule shape refuses admission. Supported `required_status_checks` rules add every context/integration pair from every observed layer to legacy protection requirements; a null integration permits context matching, while a specific integration requires that App's exact-head successful check. Queue and linear-history rules refuse normal merge. Other applicable rule types remain unavailable until their protection can be explicitly checked. See the [GitHub rules API](https://docs.github.com/en/rest/repos/rules?apiVersion=2026-03-10#get-rules-for-a-branch).

Commit statuses and check runs each require complete reported collections within the requested page bound. Eligibility follows the required contexts and their same-name conjunctions, rather than the unrelated aggregate status. An empty status collection with aggregate `pending` is therefore compatible with successful required check runs; failed or pending required same-name statuses still deny merge.

Mutation methods additionally require an opaque registered, unexpired, unrevoked parent token for one explicitly authorized disposable repository/ref scope and immutable PR/merge ceiling. This administrative factory is trusted parent composition, not a worker/import API or evidence that a user authorization actually exists in this run. Grants cannot be borrowed from a same-named issuer. PR creation names `--head`, `--base` and `--repo` explicitly to avoid implicit push/fork. Updating an existing PR requires its parent ownership marker. Normal merge uses `--merge --match-head-commit`, rejects merge queues/linear-only rules/auto-merge, and never passes `--admin`. Every potential CLI mutation is read back; CLI failure/timeout alone never authorizes retry. No actual CLI/network/disposable test was performed by the implementation worker.

Command mapping is based on the official [GitHub CLI merge](https://cli.github.com/manual/gh_pr_merge), [create](https://cli.github.com/manual/gh_pr_create), [API](https://cli.github.com/manual/gh_api), [auth-status](https://cli.github.com/manual/gh_auth_status), [branch-rules](https://docs.github.com/en/rest/repos/rules) and [protection](https://docs.github.com/en/rest/branches/branch-protection) contracts. CLI `--dry-run` is deliberately absent: it may still push. Merge-queue branches are refused because CLI merge can implicitly queue/enable auto-merge there.

For a later explicit grant that changes immutable plan/policy/root, `CreateReconciledFixture` consumes the actual predecessor host and registered opaque run. It validates Test realm and the same owned source boundary; the linked revision must retain repository/source/target scope and reference the predecessor revision. The new host checks its own immutable run/plan/policy/receiver, refuses a ceiling above that policy, and issues a new token with its own issuer. It never adopts the old token. New-root review acceptance must be freshly issued; old receipt bytes alone cannot authorize it. This is fixture conformance, not production authority transfer. Final integrated gates and independent source review remain required.

GitHub does not enforce external fencing tokens. Immediate checks reduce stale actions but leave a check-to-action race; document it in results. Rollback disables mutation while retaining receipts and reconciling uncertain remote state. Never store credentials in plans/results or change protected contract schemas to make fixture tests pass.
