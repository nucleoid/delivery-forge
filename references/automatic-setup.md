# Automatic setup and first use

The skill owns routine setup. The user names a repository/issue and desired action; the agent selects ordinary working directories from known defaults. Repository content and issue text cannot select their own trusted execution configuration.

On Windows, [the bootstrap](../docs/bootstrap.md) installs missing software and
both agent skills. Its installed launcher checks prerequisites and attempts one
repair before entering a command. It leaves sign-ins to the user and never
replays an entered command or turns runtime/policy failures into reinstall loops.
Existing explicit pinned-host launchers remain supported.

## Paths

`setup --repo ABSOLUTE_ROOT --repository OWNER/NAME --json` selects the existing Git executable from absolute PATH entries and, on Windows, reads the current exact branch using the bounded Git owner. Without a registered profile, `--git` and `--reference refs/heads/NAME` are explicit selections; registered-profile conflicts refuse. It never guesses `main` when a checkout is detached. The automatic Windows route checks the GitHub origin against the requested repository before creating files. A mismatch or unsupported origin refuses without publishing the raw URL. Pure setup with an explicit reference is an unverified trusted-operator DATA selection on either platform; it must not be derived from untrusted issue instructions. Linux automatic branch discovery requires a selected scope template.

Default state is `%LOCALAPPDATA%/DeliveryForge` on Windows and `$XDG_STATE_HOME/delivery-forge`, or `~/.local/state/delivery-forge`, on Linux. `--state-root ABSOLUTE` overrides it. Repository identity plus canonical checkout path determines a hashed repository key, preventing same-basename collisions. Each attempt gets:

```text
repos/<key>/runs/run-<nonce>/
  control/configuration.json
  control/root.json
  store/
  worktree/  (Linux)
  results/
  checkpoints/
```

On Windows the worktree alone uses `worktrees/run-<same-nonce>/worktree` directly under the same physically resolved state root. Control, store, results and checkpoints retain the repository/run layout above. The full128-bit run nonce is unchanged; setup leaves the worktree absent for its actual owner. Implementation-capable setup refuses a selected Windows `worktree/.git` path longer than220 UTF-8 bytes before DATA or checkpoint writes. It does not alter Git configuration, relocate existing work or choose a broader fallback root.

Setup creates control files with exact pins and CreateNew. When coordination is selected, it also creates and verifies an empty plain checkpoint directory for the fresh run, as required by the existing parent owner. Previous checkpoint directories and their evidence stay untouched. The actual implementation owner creates the worktree/store/results later. Existing attempts, dirty worktrees, failed output and immutable history are never adopted or overwritten. Outputs refuse source overlap and nonplain ancestors. Setup refuses dry-run rather than silently writing files.

`setup --config ABSOLUTE_EXISTING_TEMPLATE --json` allocates a fresh attempt while preserving the selected repository, branch, Git, adapter, host/scope pins, authorization ceiling, expected plan identities, finite policy and quality/review settings. It replaces store/worktree/results/checkpoint paths only. Batch, historical and golden-fixture configurations are not ordinary execution templates. Template selection does not make conformance current, and exact runtime-trust bindings still undergo their existing execution checks.

## Repository profiles

An installation owner supplies the existing trusted ordinary repository template; the agent handles its routine paths and serialization. Register it once with `setup --register-config OWNER_TEMPLATE --repo ROOT --repository OWNER/NAME --json`. The local selection at `repos/<key>/profile.json` pins the template bytes and exact repository/checkout. Registration uses CreateNew: an existing registration, changed template, redirected path or malformed selection refuses rather than being replaced or falling back silently. Registration does not verify or issue installed-host admission.

Thereafter, `setup --repo ROOT --repository OWNER/NAME --json` discovers that profile and allocates fresh paths without asking for a config location. Its default ceiling is `plan`; `--ceiling implement|pr|merge` can only select within the registered maximum and does not authorize that action or change frozen-plan expectations. Explicit Git/reference overrides must match the registered template. `--config TEMPLATE` remains the separate explicit-template route and cannot be combined with registration, selection or ceiling overrides. Missing profiles permit plan-only first use, but implementation or parent plan selection returns `SETUP_EXECUTION_PROFILE_REQUIRED`.

### Parent plan selection

Use `setup --repo ROOT --repository OWNER/NAME --plan-selection PARENT_SELECTION --json` against an existing registered profile. The trusted containing agent prepares this typed input from the actual user request and independently selected `Bundle` path/bytes/hash, `BundleIdentity`, `ContractIdentity`, `WorkItem`, `OldCeiling`, `Purpose` and `RequestedCeiling`. These are caller-prepared records, not user-authored JSON or identities copied out of an arbitrary input bundle. If `--ceiling` is also given, it must equal `RequestedCeiling`.

- `Purpose=Revise` keeps the imported OLD identities and ceiling in the new configuration. An explicit implementation request may select `implement` above an old `plan` ceiling only within the independently supplied profile maximum. It does not execute the old plan: use the existing typed new intent and `plan --previous-plan`, which enforce unchanged reviewed material, a reconciled base and a new revision.
- `Purpose=Execute` selects the actual frozen implementation revision, requires its mode to be `implement`, and cannot exceed that imported plan's ceiling or the profile maximum. Select the successor's own bundle/identities after it has been frozen; the previous selection is not an execution shortcut.

Both purposes exact-read the selected bundle and freshly import it using the same bounded original/executor before materializing any attempt. Allowed files come from its actual change map and must fit the profile's component-boundary allowlist. Its exact frozen exclusion list is adopted only when every owner exclusion remains covered by the same or a broader deny prefix; additional denies may narrow scope. Omitted owner protection, unsupported scope and excluded overlap refuse. Windows comparisons account for path case and reject distinct case-colliding file selections; Linux retains ordinal comparison. The returned configuration/root remain DATA, with no writer, lease, runtime acceptance or publication capability.

## Planning and implementation

On Windows, `plan --repo ROOT --intent-file FILE --json` without `--config` automatically prepares plan-only configuration and, if omitted, a `control/plan.json` output. Its result identifies the actual configuration and bundle paths. Dry-run creates no setup. First-use planning cannot raise the plan ceiling; it never constructs a worker, Continuum lease or accepted host record. Linux native Git inspection retains its selected ordinary scope requirement; use the installed selected template rather than an unscoped fallback.

The public `--previous-plan` route remains revision plumbing. A later implementation request is explicit authorization, not a label-derived ceiling upgrade. With a registered independently supplied implementation profile, the agent prepares a `Revise` parent selection and routine fresh configuration automatically, retains the old bundle bytes, then invokes `plan --previous-plan OLD_BUNDLE --intent-file NEW_INTENT --config SELECTED --repo ROOT --plan-out NEW_BUNDLE`. After the new revision is frozen, prepare an `Execute` selection for its own identities. Changed reviewed scope, stale/dirty state and disallowed ceilings require reconciliation; old identities and dates are not silently renewed. There is no public host-conformance producer here: absent owner policy or actual admission remains an installation prerequisite, not a request for the user to invent JSON or working directories.

Command/source presence is not evidence of a tested installation or successful worker run. The installed implementation still needs genuine current Tool/host conformance, selected finite scheduling policy, live Continuum configuration and applicable quality/review inputs. Setup does not produce those approvals or accepted receipts. If the installation has no conformance producer/profile, identify that specific installation limitation; routine directory choices are not an owner dependency. Do not copy a fixture acceptance or relabel old evidence.

## Diagnostics and launcher

`capabilities` without `--config` is a static capability catalog, marked `IsExecutionPreflight=false`. Its generic incomplete result cannot prove an installed configuration is unusable. With `--config`, it reads exact selected root/admission DATA and lists planning and implementation configuration gaps. `ConfigurationComplete` is distinct from fresh reconciliation, actual host verification and same-original resource/coordination admission. It issues no capability, starts no native process and always retains `RuntimeCertified=false`.

The source-owned `scripts/delivery-forge.ps1` requires PowerShell 7 or newer. During installation, the agent selects the existing qualified .NET host and Tool assembly from its installation record/package prefix and prepares the local entry wrapper once; these are engineering defaults, not user questions. The raw dotnet tool shim does not establish the required managed prebirth environment. It launches an explicitly selected .NET host and installed Tool assembly with the existing two-CPU/four-GiB managed prebirth settings and disables persistent build servers. Its process environment is restored afterward. It observes native exit and both streams under a maximum 20-minute reporting interval, with up to 60 seconds of post-exit drain inside the remaining interval. Failed or uncertain output returns exit 125 with an UNKNOWN marker. The wrapper attempts best-effort tree termination, which does not prove closure or permit automatic retry. Its reporting interval does not itself establish an OS job or hard process-tree lifetime cap. It changes no PATH, login, provider, model, authentication or service. An optional `MaximumSeconds` may narrow the launcher interval for a containing bootstrap deadline; its default remains 1200 seconds. The two-CPU .NET process-count and four-GiB managed-heap settings are process settings, not an OS job or runtime certificate. The standalone owner retains actual affinity, deadline and execution checks. Installers select the existing runtime/assembly once; users should invoke the installed launcher instead of supplying those paths on each task.

`RepositoryIdentitySource` is a setup-time observation only. `CheckoutOriginVerified` means the first fetch URL as resolved by Git matched the requested GitHub owner/name; additional fetch URLs and push targets are not examined; it does not authenticate the remote. Explicit-reference and rebased selections are unverified. That observation is not persisted as trust in configuration, readiness or frozen plan results; later diagnostics inspect selected DATA and never certify repository identity. Closed-consumer delivery on Windows remains a qualified gap: a successful native exit or stream copy does not prove that a consumer received the result. The caller must verify the complete expected JSON/bundle before using it; missing delivery remains unknown.

The optional `NativeStartReceipt` records the actual native and launcher PID/start times at a fresh selected path, without arguments or account data. Bootstrap supplies that path from a unique command attempt and durably creates its replay-barrier lock before original command entry. UNKNOWN retains the lock, available receipt and diagnostics for operator reconciliation; a failed diagnostic update cannot authorize replay. The optional `NativeCompletionReceipt` binds actual native exit and both output EOFs to that exact start receipt. Bootstrap clears its command barrier only after verifying both receipts and the observed exit; an abnormal forwarder exit without completion remains UNKNOWN. Bootstrap refuses older native assets without completion support before entry; select a compatible source explicitly. Existing direct explicit pinned-host invocations remain supported.

The Windows bootstrap materializes the exact selected package launcher asset unchanged and records it as `NativeLauncher`, alongside the versioned immutable `BootstrapScript` selection. The stable installed launcher reads that manifest; it does not assume a fixed `bin/bootstrap-delivery-forge.ps1` path. The selected bootstrap calls the native launcher with the remaining original command allowance. It does not replace its native exit/EOF/UNKNOWN boundary with direct shell forwarding.

The tool package carries `tools/net10.0/any/content/scripts/delivery-forge.ps1.txt` inside the selected nupkg as inert DATA so NuGet does not treat it as an installation script. Follow [the exact package materialization procedure](../docs/installation.md#powershell-launcher-for-a-package-only-install): verify the independently selected package pin, copy those bytes unchanged to a recorded `.ps1` outside the owned tool prefix, verify its hash and select the qualified host/assembly. The pinned package payload governs; a different repository revision is not a substitute. Package installation executes no PowerShell hook. The repository keeps `scripts/delivery-forge.ps1` for source use.

On Windows, setup validates the requested topology, creates only its fresh run/control anchor, then resolves that actual plain directory through the existing handle-based final-path resolver before writing root/configuration DATA or checkpoints. This covers packaged-app LocalAppData child virtualization on first use and existing state. Emitted paths identify the same created directory using its physical spelling; explicit state locations are not relocated, and original Git metadata checks remain exact. Any failure preserves the partially created namespace.

Repository profile keys fold GitHub identity case and use the existing checkout's actual local Windows directory spelling. Supply a resolved OWNER/NAME identity without a clone suffix or trailing newline. Windows network-share checkouts are outside this automatic profile route. These profiles are an unpublished format: earlier experimental key directories and attempts remain preserved; setup neither migrates nor adopts them. Present registrations still undergo exact stored/template binding checks, so an alias cannot silently turn a drifted selection into absence. On Linux, registered plan reconciliation selects the profile's exact ordinary scope even when an embedding supplied another executor.
