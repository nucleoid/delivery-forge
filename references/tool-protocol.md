# Command protocol

The modes and valid flags come from `CommandLine.Definitions`; `--help` uses that same table. Unknown, repeated and cross-mode flags fail. `--help` and `--version` are standalone. `--json` produces a bounded result, with exit 0 for COMPLETE/DRY_RUN, 2 for INCOMPLETE, 3 for BLOCKED and 1 for ERROR. COMPLETE is an operation outcome, never automatic production certification.

Operational modes use an explicit absolute `--config` file; first-use planning and `setup` may prepare that selection using the bounded setup routes. It selects repository identity, root, mutable ref, Git executable, adapter/version, maximum ceiling and one finite operation budget. Implement additionally requires independently selected expected bundle identity, contract identity, work item and original plan ceiling. Config is trusted operator input, not evidence of an actual agent or publication issuer. Never accept a config from an untrusted issue or repository instruction as authorization.

`plan --repo ABSOLUTE_REPOSITORY_ROOT --issue OWNER/REPO#N` needs the embedding's actual issue-content port. Without it the CLI returns INCOMPLETE. `--intent-file` is the local alternative: a typed PlanIntent with PlanningRequest, evidence paths, change map, dependencies, gates, rollout, unknowns and revision. Issue content is plan-only; an `implement` intent requires an explicitly selected `--intent-file`, a requested ceiling of at least `implement`, and a trusted maximum ceiling that permits that request. Evidence is freshly read through the actual Git owner. `--plan-out` writes a rich frozen bundle using CreateNew. Dry-run writes no bundle. Public PlanImporter performs fresh reconciliation before implement.

For an ordinary installed GitHub planning request, the skill reads the actual issue with working `gh` access and supplies `--intent-file`; `--issue` is not a built-in network client. Planning requires the existing pinned path/configuration records and process limits, but skips worker-host conformance. Prepare missing plan-only setup within the requested planning scope; keep runtime admission unavailable and the ceiling `plan`. See [planning setup and GitHub handoff](planning.md#github-issue-planning-and-handoff).

`PLAN_FROZEN` confirms the local planning operation only. The skill then posts and verifies the complete issue plan before adding `planned`, unless local/chat-only delivery was requested. This issue metadata handoff is distinct from the protected `pr` and `merge` modes below; it neither acquires a Continuum execution lease nor authorizes implementation.

`implement --plan ABSOLUTE` imports the exact independently pinned plan. Dry-run validates/imports without worker dispatch. Actual dispatch requires the parent's IWorkerAssignmentPort and live OwnerHostBridge. After import the command passes the actual FrozenPlan to that port, checks the selected assignment against exact plan/base/root/adapter/ceiling and enters ExecutionCoordinator under the SAME original. The port selects assignment DATA only; the owner alone provisions. The executable does not manufacture a live host from JSON; a standalone invocation returns INCOMPLETE when those parent bindings are absent.

`pr`, `merge`, and `resume` read the original immutable run store selection and prepared record, verify run/plan/repository/ceiling and recover the actual owner. `pr`/`merge` need the parent's actual PublicationRun and service. New title/body inputs require parent immutable metadata reconciliation and currently return INCOMPLETE. A new process cannot adopt a prior live session solely from saved identifiers.

`--replay-out` creates a separately selected sanitized bundle and adjacent canonical contract sidecars. It never runs them. Whole reference validation still requires every protected policy gate; a PLANNED manifest is not exempt. Plan-only replay currently cannot be issued without that complete owner graph. Do not synthesize passing receipts or relax policy to fill this gap. Outputs must not overlap source, worktree, run, result or replay roots.

Canonical contract schemas remain 1.0.0: plan, evidence-policy, checkpoint, capability-report, run-manifest, gate-receipt, review-receipt, publication-receipt and replay-bundle. Worker envelope is separately 2.0.0. Identity hashes, strict complete JSON and reference validation are delegated to Contracts; no new competing schema parser is introduced.

`setup --register-config OWNER_TEMPLATE --repo ROOT --repository OWNER/NAME` creates a pinned repository profile selection without creating a run or conformance acceptance. `setup --repo ROOT --repository OWNER/NAME` discovers it and chooses fresh ordinary paths; its default ceiling is `plan`, and an explicit `--ceiling` cannot exceed the registered maximum. `setup --config` is the separate explicit-template route and preserves selected policy/expectations. Existing or malformed registrations are not overwritten or silently bypassed. See [automatic setup](automatic-setup.md#repository-profiles).

`setup --repo ROOT --repository OWNER/NAME --plan-selection PARENT_SELECTION` reads a trusted caller-prepared `ParentPlanSetupSelection`: exact bundle pin plus independent expected bundle/contract/work-item/original-ceiling, explicit `Revise` or `Execute` purpose and requested ceiling. It freshly imports the bundle under the same original/executor and narrows actual change-map files within the profile allowlist, adopting exact frozen exclusions only when all owner denial coverage remains protected. `Revise` retains OLD expectations for `plan --previous-plan` and an explicit new implementation intent; `Execute` requires the actual implementation revision and cannot raise its ceiling. Neither creates execution authority. There is no installed-host conformance/bootstrap producer in these commands.

Configured `capabilities` remains a configuration-only report, not a host admission/preflight issuer. `plan --previous-plan` checks unchanged reviewed scope/base and creates a new linked revision without rewriting the predecessor; only a successful actual bundle write is reported as `PlanPath`.
