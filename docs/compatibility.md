# Compatibility and acceptance

The source targets .NET 10 on Linux and Windows and preserves the repository's exact global.json SDK. Contract schema 1.0.0 and worker envelope 2.0.0 are separate. Help/version/capabilities expose this distinction. No macOS claim is made.

Standalone capabilities reports named diagnostic profiles as INCOMPLETE. Live host transports and actual conformance for Codex, Claude Code and Pi are required before an adapter is called supported; OpenClaw is optional. Parent-issued publication objects remain required for genuine PR/merge. Protected review and coverage policy is unchanged.

Required pipeline chain: actual compiler RED of missing seam where applicable; fresh restore with reviewed new lock files; build and all tests; formatting; package/private-data scan; disposable Linux AND Windows install/uninstall/reinstall with actual shim and host discovery; installed live worker plus independent reviewer plus real quality and current-revision publication; recovery/cancellation/unknown outcomes. Every result applies only to its executed source and boundary. CLI fixtures, package checks and local behavioral tests do not certify the complete installed chain.

Codex app-server and Pi RPC ports use exact parent-selected task instructions. Installed runtime support requires actual conformance for the selected image and platform. Linux native commands require an explicitly provisioned creation-owned scope; missing host prerequisites remain INCOMPLETE. Windows process ownership does not certify Linux ownership.

Linux independent Claude review currently returns INCOMPLETE before native observation or review. A process scope and separate file hashes do not prove that the executed image is the exact immutable selected image. Protected changed-line coverage independently inspects the current hash-bound PE, portable PDB and captured source and compiler-source bytes. Exact context/build, module, MVID, CodeView identity, document checksum and admitted source roles must agree. The ordinary census requires usable nonhidden points for executable bodies. Its plain implicit-constructor proof requires one exact top-level, nongeneric, nonpartial class with no explicit/primary constructor, base list or initializer, and the complete standard Object-constructor IL with only permitted no-ops. The separate optimized one-await Task scaffold requires its exact metadata/IL and complete supported source vector; generated or non-class declarations disable that narrow profile. This is not general async or iterator compatibility.

When the ordinary census is incomplete, an optional official compiler recipe may establish a different, private source-origin proof. The fixed trusted Roslyn 5.9 pair must reconstruct the complete PE and portable PDB byte-for-byte, bind the entire source corpus and positively discharge authored bodies, nested carriers, initializers and constructor-argument obligations. Compiler-generated hiding or zero-point bodies are accepted only under that complete source-exhaustion proof; source-authored hiding and coverage-exclusion attributes remain blocking. Recipe labels and caller booleans cannot grant this proof, actual-task identity, freshness, measurements, a baseline or installed authority. Explicit reconstruction profile/capacity limitations leave the original census incomplete. Malformed identities, changed bytes, I/O failures, cancellation and original ownership failures remain refusals. Existing finite bounds and deadlines are unchanged.

The line policy separates the pinned Coverlet provider envelope H from required policy lines E. Each validated PDB span contributes its provider start/end envelope; required lines contain nontrivia token characters intersecting the exact half-open UTF-16 span. Comments, blanks and an exclusive next-line/column-1 endpoint earn no policy line; literal contents and punctuation remain tokens. Provider-only rows cannot earn denominator or hit credit, omitted required measurements stay INCOMPLETE, and measured zero stays failure. No coverage-attribute or generated-role exemption is inferred for changed repository files. An unsupported changed-source role or any unproven body/span/mapping in the whole module prevents a complete census, even when that source is unchanged. Token projection uses the fixed host parser, rejects conditional/remapping or unknown directives and syntax errors, and proves source-token line membership rather than expression or branch execution. Actual collector/normalizer rows still need their exact provider, build and configuration joins.

The host Microsoft.CodeAnalysis.CSharp 5.0 runtime dependency is deliberate: source-token projection and the ordinary implicit-constructor/closed-async helpers invoke its fixed parser outside the reconstruction island. Exact reconstruction separately loads the hash-pinned Roslyn 5.9 pair into its collectible context. Host parser availability does not replace exact compiler/output/source-corpus equality or establish actual-task authority.

In compiler-bound mode, each required executable line/context absent from actual measurements is unmeasured, not removed from the independently compiled denominator. A captured declaration-only input with no compiler points does not require a report-file entry; a declaration-only change still has zero measurable executable lines. Raw report DATA retains its conservative file-membership rule because it has no independent executable inventory. Unsupported document checksum algorithms remain INCOMPLETE; malformed or duplicate identities and bound SHA-256 mismatches are refused. Logical, virtual and physical compiler-document roles retain exact admitted spelling; a physical casing variant is conservatively unsupported rather than resolved through aliases. Repeated executions may combine hits only within the same context; every required context must be measured. Zero measurable changed executable lines remains INCOMPLETE, with no automatic N/A or threshold waiver. Public callable metrics retain their existing semantics. Genuine compiler-fixture controls establish only the tested metadata profile; compatibility with full unfiltered Execution, protected baseline and installed golden runs remains a separate unaccepted requirement.

Ordinary `ExecuteAsync` on Windows and Linux uses finite byte capture. Exceeding its capture limit is projected as `OwnedProcessQuiescent=false` with a bounded failure reason even when the original root exited zero. Consumers must reject that disposition; exit zero alone does not establish complete output. Native exit and EOF observations remain separate from complete output. Public capture ceilings do not extend the installed original WORK, whole or cleanup limits. Linux compatibility execution resolves the executable from the parent before applying the selected child environment. This does not establish immutable-image or creation-owned Linux authority.

Once the mandatory census is already INCOMPLETE, optional compiler reconstruction may be skipped. Partial counts can differ, and provider-membership checks that depend on a reconstructed complete context may remain INCOMPLETE rather than ERROR. Mandatory current-source, artifact, module/PDB, report/XML and ownership checks remain; skipping optional reconstruction cannot create PASS or a complete census.


### Explicit issue17 personal-host runtime trust

The owner may select `Issue17OwnerTrustedPersonalHost-v1` in the independently
pinned installed-host acceptance. This is a scoped trust decision about the
selected personal Windows host's administrator/server-managed configuration,
not evidence that safe mode inspected or disabled that policy. The containing
root must still pass the five legacy installed-host cases plus a sixth
`actual_runtime_trust_route` case for the exact selected binary and version, and
match the installed Tool image. Its sixth-case artifact must be distinct from
the other five, and its already-pinned trace bytes must bind the exact selected
image path, length, hash and version plus the complete seven-response sequence.
This structural check cannot issue conformance authority. The sixth case must actually exercise
`experimentalApi=false`, `config/read(includeLayers=true)` three times, existing
account observation before thread creation, and the actual thread model/provider.
The existing native conformance producer can observe this sequence only with an
UNVERIFIED profile; it cannot bootstrap a production admission. Schema output or
managed fixtures do not satisfy the actual route case. Only that root can bind the selection to its same
original lifetime, exact containing configuration and selected worker/reviewer.
A DTO or flag passed to a port cannot enable the profile.

The selection pins the explicit owner decision and complete selected host input
files (including explicit absence): at most 16 files, 64 KiB each, 1 MiB total.
The actual Codex-home `config.toml` and Claude configuration-directory
`settings.json` must be among them, outside parent/worker/result/review roots.
The existing restrictive Claude user-settings check remains. Repository/ancestor
Codex configuration is unsupported by this host-only selection. Selected input,
root/configuration decision or relevant environment drift revokes the same WORK
admission without renewal. Selected owner/configuration-file contents are not
copied into public receipts. Complete reviewer transcripts remain private local
evidence and may contain working directories, tool/MCP/runtime metadata, prompts
and reports. This is not transcript sanitization; inspect and sanitize that
evidence before any external export.

Known API/provider/endpoint environment overrides refuse before native birth.
Codex must observe its existing ChatGPT account before thread creation and the
actual `openai` provider with a `gpt-` model before the worker turn starts. Claude
must observe its existing first-party subscription and actual `claude-` runtime
model. No model, login, endpoint, settings or service is changed. Unobservable
administrator/server inputs are the explicit owner trust assumption; redacted

Codex transport reads effective configuration and layers before thread/turn
dispatch and again before completion acceptance. Known `openai_base_url`,
`chatgpt_base_url` or nonempty custom-provider tables refuse, including nested

also refuse. In this trust mode, configuration/account replies and other RPC

### Confined Linux Codex deployment pairing

The current Linux non-DFA Codex route requires the compatible managed Tool,
selected exact-image birth-gate closure and `nnp-user1000-ancestor-v3` scope
configuration together. This requirement applies to all such Codex workers,
including those without runtime trust; the v3 token alone issues no runtime or
review authority. Verify the complete pair before admitting new workers. A
missing or older scope refuses admission; there is no broader-write fallback.
The worker shell must preserve `GIT_OBJECT_DIRECTORY` and
`GIT_ALTERNATE_OBJECT_DIRECTORIES`. The assigned private object/index namespace
is writable; the parent common object namespace remains a read-only alternate.
Windows, other adapters and explicitly selected conformance DFA routes retain
their existing requirements. This documents the current source contract, not a
new policy, resource allowance or assertion of production compatibility.

Rollback first stops new admission and drains each actual original owner through
its existing known-close boundary. Retained UNKNOWN work remains retained. Restore
a mutually compatible Tool, birth-gate closure and scope configuration together;
do not flip the profile beneath a live original. Do not resume a private-object
worktree using an older common-only reader, delete its private objects, or use
markers as authority. Preserve failed work and evidence. Rollback does not import
private candidates or repair failed transport. No service, login,
authentication or resource-limit change is implied by this procedure.

Before a confined worker starts, its original parent anchors the exact base with
a fresh ref and moves the newly provisioned administration outside both COMMON's
worktree registry and the working tree. COMMON maintenance therefore sees the
anchored base, without reading an index or HEAD whose objects exist only in the
private namespace. Metadata, the original administration's native identity and
the base anchor are checked against the retained binding. Another worktree may
reuse the old registry name with a different identity; it is never adopted as
this run's administration. Selection is shared by the original manager and its
parent views, and confined birth refuses an unselected retained binding.

Before relocation, a bounded sibling `<private-admin>.provisioning.json` records
the run, worker, COMMON, registered/private paths, frozen base, anchor and original
marker/commondir bytes as file-flushed DATA. It grants no adoption or replay
authority. File flush does not guarantee that a newly created directory entry
survives power loss on Linux; no crash-durable journal or atomic routing rewrite
is claimed. The registered
`commondir` is made absolute and the worker marker is redirected to the fresh
private destination before the one directory move. A failed rewrite or move
therefore cannot leave the worker pointing at a freed registry name later reused
by another run. Linux relocation uses `renameat2(RENAME_NOREPLACE)` and refuses
if unsupported or if the destination appeared; Windows retains its no-overwrite
directory move. Unstarted cleanup refuses retained or observed provisioning
effects, including the deterministic ref directory and fresh-process discovery;
registry absence alone is insufficient. Its read-only ref absence query also
works for an unselected repository using another ref backend.

For partial provisioning, stop new admission and establish the actual original
owner's closure before any recovery effects. Preserve and hash the worker marker,
sibling journal, both administration locations, anchor/candidate refs and any
`.lock` files. Inspect COMMON refs independently of the worker marker and compare
native administration identities; an occupied old registry name may be foreign.
Keep the failed/UNKNOWN disposition and existing artifacts. A fresh attempt uses
a fresh destination/run association after reviewed reconciliation; neither an
older reader nor a new owner may resume, delete or adopt the partial attempt.

Only after actual writer retirement and successful canonical private-object
validation may that same parent reconcile reachable loose objects into COMMON.
An actual private-overlay traversal enumerates the candidate closure outside the
anchored base, with at most 4,096 unique object IDs. Every delta object requires
a retained validated private copy; an unprotected COMMON-only delta dependency
refuses. Unreachable private objects stay private. Forge recompresses each validated canonical body into its own
bounded complete zlib encoding; worker compressed bytes are never copied into
COMMON. Before any COMMON write, the parent reserves the known import costs and
stages canonical tree/commit/tag bodies outside COMMON. Git's strict format
check (`hash-object --no-filters -t TYPE`, without `-w` or `--literally`) must
return the exact object hashes with empty stderr. Controlled OID filename
arguments are grouped in batches of at most 48 (at most 88 native captures),
within the existing Linux 64-argument guard,
so this uses no supplied stdin or new Linux capture capability. Deferred Git
checks of attributes/modules referenced by those new objects can still refuse
within the unchanged native limits.

At most 32 existing COMMON loose collisions are compared canonically and read
by actual Git before promotion. The copy uses fresh files and no-overwrite
moves. All promoted/existing encodings must read back byte-for-byte as their
retained preflight encodings; existing encodings also passed the actual Git body
comparison. COMMON-only commit type, ancestry and targeted delta connectivity
are proved, then a fresh candidate ref is created and its value and delta are
checked again. This avoids a strict scan of unrelated historical COMMON objects.
Forward observation and review then use
COMMON alone. Private source objects, administration, base and candidate refs
remain retained; cleanup cannot import, retry or adopt a partial attempt.
Fresh base/candidate refs require Git's files ref backend. Publication holds a
fresh ordinary ref lock, refuses existing loose, packed or symbolic refs, and
uses a no-overwrite rename; a dangling symbolic ref cannot redirect publication.
Other ref backends refuse this finite profile. Failed locks remain evidence.

All object-deleting maintenance, including ordinary expiry-based `git gc` and
`gc --prune=now`, must be serialized outside promotion through the final
post-publication connectivity check. Forge's
parent admission serializes its own effects, not arbitrary external Git. This
does not claim safety against concurrent pruning during that interval.
Maintenance acceptance must exercise the separate live/private phase and then
serialize import. Only the frozen base closure is protected by the base anchor;
objects read from other COMMON refs or previously unreachable COMMON objects
have no such retention guarantee. A delta with no validated private copy refuses
before COMMON writes even if its COMMON copy currently exists. A validated
private copy is recompressed/imported even if classified as a COMMON duplicate.
Any refusal is not replay authority. Actual Linux
installed acceptance remains required.

Private-object initialization captures the complete common object-ID inventory
with `git cat-file --batch-all-objects --batch-check=%(objectname) --unordered`,
including packed objects. Its existing native capture limit is 16 MiB, within the
same remaining original WORK interval. Over-limit or incomplete capture is a
refusal before Codex birth; a truncated prefix is never a complete inventory.
Malformed, duplicate, empty or mixed-format OID inventories also refuse. This is
an availability limit, not support for arbitrary repository sizes. The later
loose-private inventory has separate existing limits of 4,096 entries, 16 MiB
per file and 128 MiB of encoded/private canonical and compared COMMON canonical
bytes; these do not enlarge the base-OID capture allowance. Type-query output
(up to 64 bytes per query), stderr capture and filesystem-operation overhead are
separately bounded by their existing capture/profile limits, not this accumulator.

Reconciliation performs an additional bounded read/canonical-comparison pass
under the same 4,096-entry, 16-MiB-file and 128-MiB combined-byte profile. It can
write at most that pass's generated encoded bytes (at most 128 MiB) to COMMON.
Source encoding, canonical content, generated encoding, COMMON collision
comparisons, structural body writes/reads, actual Git collision body reads and
exact encoded readback consume this pass's allowance. Known costs are reserved
before any COMMON write and the exact prepared encodings are reused. Passing
canonical validation alone does not reserve this separate import allowance;
an encoding or known cost refusal leaves COMMON untouched. Staged body files
remain evidence, with no automatic cleanup. The bounded preflight and promotion
each use one synchronous parent admission with chunk currentness/deadline
checks, not one retained ledger row per object. Earlier effects, the bounded
structural/collision captures and graph proofs still consume the unchanged
cumulative parent ledger. Small OID argument/output and metadata overhead remain
subject to the existing native/cumulative I/O limits, separately from this body
accumulator. All
additional metadata, object reads/writes and native
proof calls must fit the unchanged cumulative Tool/kernel limits and original
WORK interval; the profile is no new I/O allowance. Selected-run accounting must
include this pass before dispatch. No packs, fallback import or automatic
reconciliation replay is supported.

The complete bounded private inventory admits at most 32 distinct base-object
comparisons before the first COMMON query. Each comparison uses two native
captures (type and body), hence at most 64 such captures per validation. This is
a lower availability profile, not a larger resource allowance or support for
4,096 duplicates. The same cumulative parent ledger and original WORK/cleanup
endpoint can still refuse a smaller inventory. A pending or faulted validation
attempt is never usable inventory; successful forward validation includes an
explicit same-parent postcheck before publication. Ordinary async validation
refusals conservatively retain the parent's existing uncertain state, even when
no native comparison started; known native retirement does not clear it.

Source and managed controls do not replace actual Linux worker-commit,
confinement, protected-review and recovery acceptance. Current golden acceptance
and the large-inventory refusal/paired rollback scenarios remain pending; these
notes do not certify runtime behavior or resolve the other production findings.
