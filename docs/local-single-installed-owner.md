# Installed local-single owner

The standalone `LocalSingle` selection contains a `BudgetPolicy` and `RunDemand`,
under the existing independently pinned trusted configuration. Its identified
finite token/cost/time ceilings require owner approval. The current laptop's
approved two CPUs, four-GiB managed heap and one intensive lane do not supply a
numeric token ceiling. No ready or approved configuration is inferred from them.

The actual standalone caller must first establish its existing resource profile.
Composition measures that same caller's CPU/managed memory and clips the selected
resource caps to those observations. A local-real selection without an explicit
LocalSingle policy refuses before dispatch. Ordinary embedded fixture routes keep
their existing direct-execution contract.

After the actual Continuum parent acquires ownership, the bridge creates one
LocalSingle scheduler from the same frozen plan, exact base/scope, original
lifetime, admitted Git view and execution store. It calls `ReserveAsync` followed
by `ProvisionAndPrepareAsync` once. The latter provisions the absent disposable
worktree and prepares the worker; the bridge never prepares it a second time.
The frozen dependency integration conditions must resolve to integrated commits.

Every scheduler wait and deadline is clipped to the existing original WORK
endpoint. Store effects, provisioning Git and dependency-read Git are admitted
by the same parent. No scheduler stopwatch can renew ToolLifetime. The live
reservation spans the worker, installed quality, independent review and fixture
publication phases.

After the exact retained pipeline task settles, a private completion path checks
the same native/IO/control closure, immutable completed receipt, live writer and
current parent. It records completion, disposes that actual writer and releases
the reservation without sending Stop after LocalComplete. Known stopped runs
instead use their same original cleanup allowance and actual stopped record;
uncertain tasks, processes, writer disposition or finalization retain capacity.
Saved checkpoints cannot invoke these private same-process release paths.
If the actual base check refuses before provisioning or preparation was entered,
the exact settled no-start pipeline can release its ticket under that same
original cleanup allowance. Unknown provisioning, store-handle uncertainty and
uncertain reservation persistence retain capacity and failure evidence.

`SchedulingCertified` and `RecoveryCertified` remain false. The source and narrow
fixture controls are not installed behavioral acceptance or cold recovery proof.
The next acceptance is a fresh installed local-real run with an independently
approved finite LocalSingle policy, plus failed/blocked/stop behavior under that
same original. Normal restore must update Tool/Tool.Tests lock graphs for the new
Scheduling project reference before the next locked restore and build.
