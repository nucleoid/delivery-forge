# Removal and reinstall

Use the independently retained `InstallationReceipt`. Removal verifies every original owned payload hash, executable mode, claim, manifest and complete prefix topology before deleting anything. Changed/missing/foreign files or directories refuse removal, preserving user data. External runtime-host servicing does not itself prohibit removing unchanged owned files; public `Verify` still checks the host pin when installation/launch trust is needed.

`BeginRemoval` creates a distinct new sibling recovery directory with a pinned immutable plan. Retain its actual `RemovalReceipt` before calling `ContinueRemoval` if recovery DATA must survive the caller. `ContinueRemoval` validates that exact plan and every remaining original before effects. Each deletion has separate CreateNew entered and returned records. A missing actual returned record is UNKNOWN and refuses replay, even when a path is now absent or a later observation suggests that a delete was not applied. Deadline/cancellation checks before and after effects remain mandatory. A failed post-check cannot refund the deadline or turn absence into known return. A completed step is not retried. Journal files remain ordinary evidence after success; they are not a runtime capability.

`Uninstall` wraps these APIs and attaches the SAME actual `RemovalReceipt` to the primary exception's `ActualRemovalReceipt` DATA if continuation fails. This does not claim durable export, automatically resume an unknown step, or reconstruct ownership from a directory name. Partial journal/prefix state is retained. Prefer the explicit two-stage API when the caller needs to persist the receipt before deletion.

`Reinstall` reads and completely validates one bounded archive byte array and the same payload identity before removal, then installs from that SAME private byte array/derived complete payloads into the now-new prefix. It does not reread a replaceable archive path after removing the old installation. A true post-create write/deadline failure retains its partial prefix and ordinary failure DATA; there is no recursive rollback, deletion of failure evidence or adoption of an existing prefix. External hostile concurrent namespace changes remain outside this cooperative profile; reparse and known-drift checks remain mandatory.

Per-archive/manifest entry limits do not guarantee sufficient remaining cumulative file credits for an arbitrary large removal or multiple lifecycle operations in one original. Current complete-operation/read/write/deadline caps are unchanged; no reservation framework, refund, renewed owner or out-of-budget effect is implied. Actual interrupted-removal/reinstall and both-OS installed golden proofs remain separate requirements. Manual reconciliation of an entered-only operation needs the original failure evidence; automatic retry is unsupported.
