# Quality gates and evidence receipts

## Layered evaluation

1. **Meaningful RED/GREEN** — show the intended behavior fails for the right reason, then passes after implementation.
2. **Affected tests** — cover changed behavior, callers, contracts, and known impact surfaces.
3. **Required full/build gates** — satisfy repository policy with clean builds/full suites where required.
4. **Complexity and coverage debt** — measure changed-code risk and prevent unapproved threshold/baseline regression.
5. **Mutation strength** — use survivors to drive real behavior tests; enumeration must be complete enough for the claimed scope.
6. **Independent cross-family review** — review the exact patch/head with a genuinely independent model/tool family where policy requires it.

Scope is risk-proportionate. Documentation-only work may mark code/test/mutation gates `NOT_APPLICABLE`, but each N/A needs a concrete reason.

## Gate outcomes

Every gate returns exactly one outcome: `PASS`, `FAIL`, `INCOMPLETE`, `ERROR`, or `NOT_APPLICABLE`. Timeout, unsupported capability, missing coverage/artifacts, truncated results, or incomplete mutation enumeration never map to `PASS`.

## Deterministic evaluation plugins

Gate execution resolves a trusted, code-registered deterministic evaluation plugin. The built-in .NET test, Crap4CSharp, and Mutate4CSharp adapters retain their existing default-enabled gate behavior behind compatibility wrappers. Trusted host code may register another implementation by stable ID/version/tool identity; frozen plans can select only registered IDs and cannot supply executable plugin code or commands.

Plugin configuration records an explicit enabled state. Disabling a selected required gate yields `INCOMPLETE`; it is evidence metadata, not a policy bypass. One code-owned gate/plugin registry drives protected-policy resolution, evidence writing, and consumer authority checks, including .NET, Crap4CSharp, Mutate4CSharp, and anti-slop mappings. An unmapped required gate remains unsatisfied and non-authoritative.

### Host integration status and opt-in path

The library exposes the anti-slop integration, but no supported production launcher or orchestrator in this repository invokes it automatically. `DeterministicEvaluationPluginRegistry.CreateBuiltIns(trustedAntiSlopBundleRoot, trustedNodePath)` registers the bundled plugin, and `SelectApplicable(configurations, candidateInputs, ignoredInputs)` automatically selects JavaScript-family inputs once a host calls it. Today those selection and request-composition APIs are called only by tests. The only non-test end-to-end `GateRunner` composition is the CrashDriver, while `AuthoritativeEvaluationHost` deliberately throws `NotSupportedException`.

An integrating host would use the following **pseudocode** (policy, capability, repository identity, paths, scope, timeout, output, runner dependencies, and cancellation are host-owned values):

```csharp
var registry = DeterministicEvaluationPluginRegistry.CreateBuiltIns(bundleRoot, nodePath);
var selections = registry.SelectApplicable(
    [new EvaluationPluginConfiguration("dmmulroy.anti-slop", Enabled: true, EnableEffectRules: false)],
    candidateInputs,
    ignoredInputs);

foreach (var selection in selections.Where(x => x.Enabled && x.Inputs.Count > 0))
{
    var request = AntiSlopRequestFactory.Create(/* host-owned gate and repository values */,
        inputs: selection.Inputs, enableEffectRules: selection.EnableEffectRules);
    await gateRunner.RunAsync(request, cancellationToken);
}
```

Set `Enabled: false` to retain explicit disabled metadata; a required disabled gate is `INCOMPLETE`, not bypassed. Detection is case-insensitive for `.js`, `.jsx`, `.ts`, `.tsx`, `.mjs`, `.cjs`, `.mts`, and `.cts`. In a mixed-language candidate set, only those JavaScript-family paths are selected; other paths remain available to their applicable gates. Host-supplied `ignoredInputs` are excluded during selection, and execution additionally honors the protected-base `.delivery-forge/anti-slop-ignore` contract described below. The five Effect rules require `EnableEffectRules: true`; the default is false.

Accordingly, the framework, adapters, plugin, and tests are implemented, but automatic production invocation remains open integration work, blocked here by the absence of a supported host and paused runtime wiring. This PR must not be described as satisfying automatic runtime invocation.

The bundled `dmmulroy.anti-slop` plugin derives JavaScript-family files from the exact frozen Git tree. Regular tracked files are mandatory unless their exact paths occur in the optional protected-base `.delivery-forge/anti-slop-ignore`; patch-head ignore changes have no authority. Paths, blob ids, Git modes, include/exclude decisions, and retired protected ignores contribute to the complete tracked-head identity. Protected ignores may exempt an explicitly named non-regular entry, and stale entries are retained as retired identity evidence rather than deadlocking a deletion or rename. Selected blobs are obtained through bounded `git cat-file --batch-check` and `git cat-file --batch` groups, verified in memory with Git's object hash, and written byte-for-byte to a fresh private host-owned root outside the repository. They are made read-only, linted there using repository-relative paths, and removed after receipt persistence. This preserves the committed bytes despite checkout filters, `autocrlf`, smudge/LFS behavior, or index hints such as skip-worktree and assume-unchanged; repository cleanliness is bound separately. The receipt records the frozen object/input-set identity and a deterministic logical materialization label, not the random private path. Object/file/aggregate counts and sizes are bounded, paths are consumed from NUL-delimited Git output, and all phases consume one finite gate deadline; a missing/malformed object, ambiguity, cancellation, or exceeded bound is `INCOMPLETE`.

Protected ignored paths are not suppression-scanned. The production scanner is byte-, directive-, rule-, body-, file-, aggregate-byte-, per-file-line-, aggregate-line-, time-, and nesting-bounded and uses an explicit template-state stack. Limits are 4 MiB and 262,144 logical lines per blob, 64 MiB and 1,000,000 logical lines across base plus head, 1,024 directives, 256 rules per directive, and 16 KiB per directive body. It retains compact SHA-256 line anchors rather than source copies or hex-expanded lines. A head directive is inherited when its semantic scope/rule, directive bytes, and complete covered content match a base directive; this allows an unchanged directive/content block to move while rejecting widened coverage, deleted `enable`, or inherited blanket coverage over changed code. A rule-specific enable does not terminate an open blanket disable. Common unrelated bare rules (`no-console`, `no-unused-vars`, `eqeqeq`, `prefer-const`) are classified safe; anti-slop aliases, `eslint/no-accumulating-spread`, slash-qualified aliases whose suffix is an anti-slop rule, blanket directives, and unknown bare ambiguity fail closed. Keyword/property division and JSX/TypeScript ambiguity—including slash-leading JSX text, brace-bearing quoted strings inside JSX expression containers, JSX-shaped syntax inside a template expression, and any non-comment slash inside a template expression—have exact scanner regressions and real pinned Oxlint fixtures. ASI-separated `return`/`throw`/`yield`/`await` regex prefixes, `export default` and `extends` regex contexts, `for await (... of /regex/)`, and byte-zero or BOM-prefixed hashbangs are classified explicitly. Keywords after `.` or `#` remain property/private-field names across line terminators. A slash directly after `<` or `++`/`--` is conservatively ambiguous. Exact suppressed and unsuppressed controls prove Oxlint's directive semantics for these shapes. Pinned Oxlint 1.78.0 treats BOM followed by hashbang as a parser error, which is `INCOMPLETE`; its `eslint/no-accumulating-spread` directive suppresses the configured `oxc/no-accumulating-spread` rule and is therefore dangerous coverage. The template-regex and exact reviewed template-JSX fixtures likewise retain matched controls. Any lexical ambiguity or exceeded cap is `INCOMPLETE`, never PASS.

Its invocation is read-only and canonical. `AntiSlopRequestFactory` is the public code-owned request path: it performs bounded structural composition, selects direct argv within a deterministic 24,000-byte budget or atomically creates a bounded content-addressed JSON manifest for the batch host, and leaves closure identities explicitly unavailable. Larger sets use the code-owned Node batch host; it uses argv arrays (never a shell), finite batches, bounded output, exact aggregate file/rule counts, and the same outer containment. Manifest/path/batch/diagnostic sizes are capped. Every Oxlint child receives the shrinking remainder of one shared deadline, and .NET owns the Node/Oxlint process tree so timeout or cancellation kills the whole tree. Only the exact 19 generic rules run, with five Effect rules added by explicit opt-in. The reviewed Linux x64 GNU closure digest binds package/lock/config/batch-host bytes, all vendored anti-slop sources, `@oxlint/plugins`, the complete Oxlint package/JS launcher, the native binding, and Node executable bytes; base and Effect-opt-in closures have separate pins. After claim creation, gate execution takes one async pre-execution snapshot under the remaining shared deadline. Directory enumeration checks cancellation, file reads use the deadline-linked token, closure caching has an explicit 256 MiB ceiling, and the captured configuration/runtime/executable identities are reused by validation, execution, audit metadata, and receipt binding without later synchronous closure recomputation. A pre-snapshot receipt records configuration and runtime closure as `unavailable`; a successful snapshot replaces both with the captured identities and replaces the result's deleted materialization path with the stable logical working-directory label. Missing, corrupt, cancelled, oversized, or pin-mismatched closure files, native bindings, or Node bytes persist `INCOMPLETE` through the no-execution receipt path. Because the current same-UID host cannot make the installed closure immutable against itself, it does not claim post-snapshot mutation detection and future-v2 authority remains disabled. V2 bindings carry the runtime closure identity and the trusted registry validates it downstream. Fixture-only `tsx` and TypeScript are pinned for fixtures but excluded from production runtime authority. The frozen materialization is re-enumerated and every file is re-hashed to its expected Git blob identity after Oxlint exits. Frozen roots are deleted on normal completion, timeout, and cancellation; owner sidecars let a later run recover roots whose creating process died, while active owners are retained. Syntax/parser/tool/start/runtime failures, missing Node/Oxlint/native binding/`setsid` support, unsupported platforms or reports, incomplete counts, changed frozen bytes, and cap/deadline failures are `INCOMPLETE`; policy findings are `FAIL`. Zero applicable files never pass.

External code-owned plugins register through one `TrustedEvaluationPluginRegistry` entry per gate. Each entry binds the implementation, stable plugin/tool identities, expected tool/format versions, and optional runtime-closure identity together; repository policy may select a registered id but cannot register an implementation or supply a command.

## Receipt contract

Every receipt records gate/policy IDs; base/head/tree; tool version and detected capability; config and baseline identity; exact command/invocation; scope; timestamps/exit state; outcome/reason; artifact paths/hashes; limitations/exclusions/missing data/N/A rationale; and whether source/tree changed during evaluation. Receipts are append-only evidence; summaries cannot erase failures or limitations.

Canonical gate receipt v1 remains the public `GateRunner` output with the protected-base schema, field set, and serialization; plugin metadata is not injected into that command envelope. Existing legacy-adapter v1 command-envelope bytes remain unchanged, while anti-slop replaces only its ephemeral materialization directory value with the stable `<host-owned-frozen-inputs>` label. Existing v1 consumers continue to accept schema-valid, exact base/head/tree/policy-bound `PASS` and policy-allowed `NOT_APPLICABLE` receipts. The default code-owned built-in execution registry retains that legacy-v1 producer path under the original protected-policy, required-gate, non-fixture, detector-verified policy-range capability, pinned report format, and production-capable checks; exact registry tool-version pins remain future-v2 bindings and do not retroactively narrow canonical v1. The same registry entry marks whether a gate has legacy-v1 authority. Fixture capability, externally registered plugins, caller-injected registries, disabled gates, patch-selected implementations, and anti-slop cannot mint legacy-v1 authority. `GateRunResult.Plugin.PluginRawOutcome` and the future-v2 envelope name the pre-integrity-override plugin result explicitly; v1 receipts contain no PASS-shaped plugin summary field. Every completed anti-slop v1 persistence hashes `anti-slop-binding.json`, a deterministic sidecar containing plugin/version, configuration/runtime closure, exact repository and input-set identities, tool capability, raw/final outcomes, and the truthful authority classification. The current same-UID path records `advisory`; a future authorized producer can record `production-capable` without changing v1 schema. The sidecar is evidence, not correctness authority.

Future-v2 authority remains disabled on this same-UID host. `AuthoritativeEvaluationHost` construction is unavailable, the public runner emits v1 only, and the immutable production `GateReceiptConsumerPolicy` is `Disabled`. The future-v2 envelope carries `plugin.runtimeClosureIdentity` and `plugin.pluginRawOutcome`; its authority consumer validates the runtime closure and does not treat the raw outcome as final authority. Serialized/per-call `TransitionEvidence` and `PublicationRunDefinition` flags cannot activate enforcement. Fixture-only policy construction exists only for isolated contract tests. `HostOwnedReceiptStore` and v2 readers remain compatibility primitives, not proof that an authoritative producer exists.

V2 activation has an external deployment prerequisite: a separately privileged executor/signer must keep signing material, frozen inputs, claims, and the receipt ledger inaccessible to the patch process and same uid. Only a future code-owned host adapter that enforces that boundary may mint an activated immutable consumer policy. Rollout remains producer-first: deploy and verify the privileged producer and exact registry/closure identity before replacing the disabled consumer policy. Existing canonical v1 receipts remain readable and retain their legacy acceptance semantics during mixed-version rollout; deployment must not silently invalidate them or broaden their trust beyond the built-in legacy-v1 gate. Rollback is consumer-first: restore the immutable disabled policy, retain v2 readers/provenance until live work drains, then stop the producer. Never self-compare caller-provided registry identities or treat fixture keys as activation evidence.

Never promote v1 as fallback authority after activation. Claims are written and flushed to a same-directory temporary file, atomically renamed into place, and held with an advisory lock. They bind PID, boot, process-start identity, nonce, and acquisition time. Verified live locks exclude concurrent runs; stale/torn/malformed unlocked claims are atomically displaced, preserved for diagnosis, recorded as `INCOMPLETE`, and permit a later retry. Reparse claims fail closed. A later acquisition inspects at most 64 unpublished pending claims and removes only non-reparse files older than ten minutes; fresh concurrent pending files remain untouched. Every execution publishes directly into a fresh immutable `.attempt-<nonce>` directory, so interruptions cannot reserve a canonical result directory.

Host Git reads reject repository-local `filter.*`, `include.*`/`includeIf.*`, and `core.attributesFile` configuration before invoking Git, suppress system/global configuration, override hooks/fsmonitor/attributes, and verify the local config byte identity did not change across each identity/scope capture. Patch-controlled clean/smudge/process filters are never executed by the host read path.

The built-in `ci` authority is an explicit external-issuer boundary: Delivery Forge does not produce CI receipts. A trusted host must translate an authenticated GitHub Actions/Checks result for the exact head into tool version `github-actions-v1` and format `github-checks-v1`, then append the receipt to a host-owned append-only store. Repository files and workflow-produced patch artifacts are inputs only and cannot establish authoritative receipt provenance.

## Baseline and policy ownership

Roll out from advisory reporting to reviewed baseline/exemption registries, then enforce no unapproved changed-code regression. Workers cannot weaken thresholds, omit required projects, broaden exemptions, regenerate a favorable baseline, or self-approve policy changes. Mutation survivors prompt stronger behavior tests, not suppression.

## Exact-patch review

Independent review binds to base/head/tree and exact patch hash. Edits, amend, rebase, conflict resolution, generated changes, or dependency integration trigger invalidation assessment. Material patch changes require fresh review.

## Failure scenarios kept visible

Stale plan/changed base; conflicting writer/uncertain lease; interrupted command; incomplete mutation enumeration; missing/stale coverage; baseline/exemption gaming; review of another patch/head; green partial tests without required full gates; and installed tools lacking required capability.
