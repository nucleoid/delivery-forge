# Disposable installation

The package is a .NET 10 PackAsTool artifact containing the actual tool and thin skill/reference documentation. No global installation, PATH, agent config, authentication or service is changed by this source slice.

`PackageLifecycle.Install` requires a new absolute Linux/Windows prefix and an independently pinned actual runtime host. It reads the bounded archive once and validates every complete entry, required payload role and owned payload topology before creating the prefix. Traversal, aliases, special files, private paths and secrets refuse before prefix birth. It then writes only the prevalidated tool runtime subtree, creates a platform shim and verifies complete file AND directory membership. The exact claim/manifest/receipt must be retained independently. This custom prefix API does not assert that `dotnet tool install` has run or that an agent discovered the skill.

A true filesystem/deadline failure after prefix creation preserves the partial prefix and available failure DATA (nonce, package hash, known returned file rows and last attempted path). That DATA is not a durable receipt, an accepted installation, permission to adopt a prefix, or an automatic rollback/removal protocol. Existing prefixes remain refused.

The public CI workflow prepares a genuine package and includes the BCL-only execute-mode lifecycle control on Linux; that control uses inert gate bytes and conditionally skips other operating systems. Installed-package golden, standard tool-install and separately admitted native/live cases remain excluded. A green public job therefore does not prove genuine package installation, shim execution, native Linux gate launch, skill discovery or live acceptance. The separately admitted `InstalledPackageGoldenTests` and `StandardToolInstallTests` define installed acceptance routes; their required fixtures cannot be replaced by inert bytes or absent-input success. Current Windows SDK install/shim/uninstall/reinstall evidence remains scoped to its exact tested package. Linux installed/native acceptance and genuine host skill discovery remain separate required gates; macOS is unclaimed.

The custom Linux prefix sets and verifies mode 0700 for its owned gate apphost. That says nothing about executable-mode preservation by the SDK tool installer. Actual Linux scope launch requires the independently selected complete five-file gate closure/build history, resource profile and kernel/user-manager prerequisites. It hashes the selected closure and actual `/proc/<owned-pid>/exe` at the private birth barrier before releasing a target; there is no legacy/native fallback if startup, READY or identity fails. The gate is a framework-dependent apphost and still depends on the supported installed runtime/loader platform; the custom tool shim's pinned host does not establish that separate runtime binding. Missing mode/runtime and unresolved scope/image prerequisites cannot be promoted into Linux capability.

For arbitrary Windows arguments, invoke the pinned runtime host directly with `DeliveryForge.Tool.dll` as the first `ArgumentList` entry and each remaining argument separately. The custom `.cmd` shim is convenience for fixed trusted literal arguments; its `%*` forwarding uses cmd parsing and is unsuitable for untrusted text or general shell metacharacters. The SDK-generated native shim is a distinct installation route.

Archive bounds (2048 entries, 64 MiB compressed, 256 MiB complete expanded bytes, 16 MiB per entry) and owned manifest bounds are finite admission ceilings, not promises that every such archive completes a lifecycle. The same original also has cumulative 4096 complete-file-operation, 1 GiB read and 256 MiB write credits and unchanged WORK/whole deadlines. Prior operations consume those credits. No new budget, credit refund or late cleanup is granted by installation. Source presence and public CI are not installed-outcome certification; locked restores and actual payload/source joins remain mandatory.
