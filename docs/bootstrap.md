# Windows bootstrap and automatic first-use repair

The source entrypoint is [`scripts/bootstrap-delivery-forge.ps1`](https://github.com/nucleoid/delivery-forge/blob/main/scripts/bootstrap-delivery-forge.ps1), run from a selected clean checkout or saved as a standalone source file.
It works from Windows PowerShell 5.1 and installs PowerShell 7 if needed. It can
also be downloaded as one file: the installed launcher is generated by the script,
so an adjacent source checkout or second downloaded script is not required.

Inspect prerequisites without installing anything:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\bootstrap-delivery-forge.ps1 -Mode Check
```

Install all automatable prerequisites, the CLI and both skills:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\bootstrap-delivery-forge.ps1 -Mode Install -SourceRoot (Get-Location).Path
```

An agent can use `-Json` with either mode. The report includes every missing or
unverified prerequisite, exact remediation steps, automatable actions, user
actions, installation readiness and authentication readiness. It does not print
credentials or retain raw authentication-status output.
The example's execution-policy setting applies only to that PowerShell process;
it does not change machine/user policy or override an organization's enforced
application-control rules. Review a downloaded script before running it.

The script checks Git, GitHub CLI, Codex CLI, Claude Code CLI, PowerShell 7, the
exact source-pinned .NET SDK, installed CLI startup and both skill installations.
Node.js is checked/installed only when an existing npm-based Codex installation
needs it; the default native Codex install does not introduce a Node requirement.
It uses WinGet's exact package IDs for missing command-line tools. It does not
reinstall an existing executable whose probe was denied or failed: those cases
need diagnosis rather than a second installation. If WinGet/App Installer is
unavailable, the report gives the official installation link. Windows may require
the owner to approve an installer/UAC prompt; the script does not elevate itself
or switch Windows users.
Prerequisite entry points must be native executables or supported `.ps1` scripts.
A tool found only through a `.cmd`/`.bat` shim is preserved and reported as
unsupported; bootstrap does not run it or install a competing copy automatically.

On a first install with no source selection, a fresh checkout of
`nucleoid/delivery-forge` is retained under the attempt and `main` is resolved to
an exact commit before build. Use explicit `-Ref COMMIT_OR_REF` to select a
revision, or `-SourceRoot ABSOLUTE_CLEAN_CHECKOUT` to select an existing checkout.
With `-SourceRoot` alone, its current HEAD is selected. If both are supplied, the
requested ref must resolve to that HEAD; bootstrap never changes the checkout.
A standalone downloaded script without `-SourceRoot` selects remote `main`.
The installation records the executing bootstrap and selected source-bootstrap
hashes separately and reports whether they match.
Repair of an existing installation without either explicit selection keeps its
recorded commit and reuses its retained clean source when available; otherwise
it obtains a fresh checkout of that same commit. Automatic repair does not
upgrade to a moving branch. Existing dirty source is never reset, stashed or
cleaned. The checkout must contain the CLI and root `SKILL.md`.

The SDK version comes from that checkout's `global.json`. A missing SDK is
installed privately, with Microsoft's installer, under
`%LOCALAPPDATA%\DeliveryForge\sdk\<version>`. The build restores the locked project
graph from nuget.org, builds the Linux gate payload and Windows CLI, packs the
tool, installs only from that newly prepared local feed, and runs real help/version
startup checks. Build servers are disabled, SDK process count is two, the managed
heap ceiling is four GiB. Bootstrap uses one original twenty-minute deadline
for prerequisite probes, repair and command reporting.
The process-count and heap settings are .NET process settings, not OS CPU/RAM
enforcement or certification of an agent execution runtime. The exact
resource-aware launcher asset from the selected package is materialized unchanged
and hashed as the installation's `NativeLauncher`. The shared bootstrap logic is
retained as its immutable versioned `BootstrapScript`.
The native launcher receives only the remaining original command allowance and
observes native exit and both output streams. These reporting deadlines do not
create an OS job or establish a hard process-tree lifetime bound. An independently
admitted execution owner must still enforce its actual execution limits. On
uncertain native/output completion the wrapper attempts best-effort tree
termination and retains UNKNOWN; a kill attempt does not prove closure.

The default layout is:

```text
%LOCALAPPDATA%\DeliveryForge\
  bin\delivery-forge.ps1                 stable manifest-selecting launcher
  installation.json                     selected hashed installation
  installations\<commit>-<nonce>\        isolated CLI payload
  sdk\<exact-version>\                   private SDK, when required
  bootstrap\attempt-<nonce>\             source, build/install logs and reports
  bootstrap\command-<nonce>\native-start.json  native PID/start observations

%USERPROFILE%\.agents\skills\delivery-forge\   fresh Codex skill
%USERPROFILE%\.claude\skills\delivery-forge\   Claude Code skill
```

The installation record selects and hashes the versioned `BootstrapScript` and
`NativeLauncher`; a fixed `bin/bootstrap-delivery-forge.ps1` path is not required.
For an installed `Check` or `Install`, the agent reads and verifies that existing
record, then invokes its selected `BootstrapScript` with `-StateRoot` set to the
record's containing installation directory. This also preserves a custom state
root instead of falling back to the default. This is routine setup: users do not
choose a helper path or write installation JSON. The stable launcher uses
the same selected bootstrap automatically before a Forge command.

`-StateRoot ABSOLUTE_DIRECTORY` overrides the installation root. It must be on
the same volume as the selected skill destinations, because activation uses
atomic directory moves; a cross-volume choice refuses before installation steps.
The script avoids an agent's disposable AppContainer LocalAppData redirect when
choosing its default.
An existing Codex installation under `.codex/skills` or `.agents/skills` is
respected; bootstrap does not create a competing same-name skill. Conflicting or
customized installations are preserved and reported for resolution.
UNC, relative, symlink and junction paths are refused. No persistent PATH change
is needed; both installed skills contain the explicit launcher path. A new agent
session may be needed before skill discovery refreshes.

## Automatic bootstrap before a run

Invoke the installed launcher, rather than the SDK-generated raw shim:

```powershell
& "$env:LOCALAPPDATA\DeliveryForge\bin\delivery-forge.ps1" plan --repo ABSOLUTE_ROOT --intent-file ABSOLUTE_INTENT
```

For arguments that must remain exact strings, prefer an explicit PowerShell
`-File` invocation. Both `-File` and `/File` preserve native arguments, including
trailing-colon strings. Windows PowerShell 5.1's implicit script invocation uses
command parsing and is refused. Direct invocation accepts ordinary string-array
splats, but refuses nested argument collections and ambiguous dash-prefixed
trailing-colon values; use explicit `-File` for those values. Bootstrap reports
these cases instead of reconstructing a PowerShell expression. Explicit stdin
is unsupported when a `.ps1` prerequisite needs the script transport, including
an explicitly empty stdin value. Routine command examples above remain valid.

Before starting the actual CLI, the launcher checks prerequisites. If installable
dependencies are missing, it runs bootstrap once and rechecks the installation
within the original twenty-minute invocation deadline. It then invokes the pinned
resource-aware launcher for the original CLI command once. It never repeats an implementation,
publication or other already-entered command after a failure. Authentication-only
failures do not trigger reinstalling. Runtime admission, Continuum, policy and plan
reconciliation failures are not repaired by reinstalling or relabelling receipts.

The bootstrap never runs `gh auth login`, `codex login` or `claude auth login`.
It prints those exact actions when needed, checks subscription login rather than
accepting API billing as equivalent, and checks `gh` without refreshing its token.
It detects `--no-refresh` from the installed help and supplies it when supported.
The exact legacy 2.86.0 status route is separately supported as read-only; other
versions without a known refresh-suppression policy remain unverified. See the
[current manual](https://cli.github.com/manual/gh_auth_status) and the
[2.86.0 source](https://github.com/cli/cli/blob/v2.86.0/pkg/cmd/auth/status/status.go).
Provider-override environment variables are reported by name only and left intact.
Full `Check` reports all tool and authentication states. Command readiness uses
only the tools and authentication needed by the command. Exact `--help`/`--version`
and `MODE --help`/`MODE --version` diagnostics do not probe unrelated workers,
GitHub sign-in, SDKs or skills. Local recovery does not require new worker sign-ins.
Planning/setup
do not require worker subscription logins. GitHub issue reading or posting needs
the user's GitHub access; the containing agent verifies it before that operation.
After completing a genuinely required browser sign-in, run the original command
again only when the CLI command was not entered.

Checks and scripts do not grant implementation, publication, merge or deployment
permission. Genuine host admission, current Continuum configuration and repository
quality/review policy must still be supplied to the actual execution owner.
`ExecutionCertified` is always false in a bootstrap report.

## Preservation, reruns and agent contract

- Exit `0`: all checks requested by this invocation are ready. This is not an
  execution certificate.
- Exit `2`: prerequisites or human actions remain; use the complete report.
- Exit `1`: an entered installation/build step failed; inspect its attempt logs.
- Exit `125`: native process/output disposition is UNKNOWN. Retain the attempt
  and `bootstrap.lock`; do not remove the lock or retry automatically.

Intact managed skills can be reused. Missing managed files can be repaired, and
unchanged managed skills can follow an explicitly selected source revision. The
entire prior directory is retained under `bootstrap/skill-backups` first. An
existing unmanaged or edited skill (including additional untracked files) is
preserved and reported as a conflict; no automatic overwrite is attempted. Failed
CLI prefixes and source/build evidence remain in their attempt directories. A
second invocation uses a fresh attempt rather than adopting a partial prefix.
Before the original CLI can start, bootstrap creates and flushes `bootstrap.lock`
as a replay barrier. It records the containing PID/start time and points to the
unique command attempt's `native-start.json`; after native birth that receipt
records the launcher and actual native PID/start times, without argv or account
data. A matching `native-completion.json` records the native exit and both output
EOFs, bound to the start receipt. Only that verified completion can clear the
command barrier; a forwarder exit alone cannot. Older bootstrap payloads without
this capability refuse before entry and require an explicit compatible source.
Pre-entry probe UNKNOWNs retain their observed PID/start context separately.
UNKNOWN retains the lock, available receipts and diagnostics for an operator.
A failed receipt or diagnostic update does not authorize replay. Do not delete the
lock or infer closure from a PID alone: inspect the exact PID/start observations
and reconcile process/output state first. Best-effort termination remains UNKNOWN
until independently resolved.

`Check -Json` is a complete inventory, including tools not required for the next
command; a held lock reports authentication as unobserved, not ready. Agents must
act only on prerequisites relevant to the requested operation. The installed
launcher performs that scoped check automatically.

An agent's first-use workflow is: run `Check -Json`, run `Install -Json` when there
are automatable actions, explain only the remaining human actions, and use the
installed launcher for subsequent Forge commands. Do not request routine directory
choices, copy credentials, select a different model/provider, fabricate runtime
acceptance, or treat the static capabilities catalog as installed-host conformance.

## Validation and scope

Run the source-owned PowerShell controls without installing prerequisites:

```powershell
pwsh -NoProfile -File .\scripts\tests\bootstrap-delivery-forge.Tests.ps1
```

These exercise reports, authentication-routing decisions, preservation, filesystem
behavior, one-time automatic repair and actual native argument transport. Public
CI runs the source-owned controls on Windows and retains their JSON results.
Their fixture or simulated-install results do not prove real installation. Real
restore/build/package/private-install, idempotence and help/version results are
accepted only for their observed subscopes; they do not turn a failed whole
attempt or unfinished repair-then-command check into PASS. A warm-machine run and
a clean Windows laptop/VM installation are separate acceptance scopes. Neither
manufactures host conformance or repository execution authority. The bootstrap
does not provision a Linux guest, enable WSL/Hyper-V, install a Continuum service,
or claim macOS/Linux installer support.
