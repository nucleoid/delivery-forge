# Linux exact native image profile

The optional exact-image mode binds the selected main native ELF image to the
creation-owned Linux scope. It does not enable protected Linux review. The reviewer also refuses a missing
selected Linux scope or a nonmatching configured capture executor/original
budget before evidence preparation; this admission check launches nothing. The
managed birth gate, its runtime, the ELF interpreter and dynamically loaded
libraries remain a separate trust boundary.

Ordinary command scopes may still omit exact-image mode. Linux Codex, Claude
stream-json and Pi RPC worker ports require a selected scope and the exact sealed
main ELF image before protocol startup. They reserve the existing complete-read
credit before pathname hashing or native birth and require their retained owner's
actual exact-image proof before any protocol work. Missing scopes, oversized
images and scripts refuse; there is no ordinary-image fallback. This enforces
image binding, not authentication, installed CLI compatibility, runtime-trust
admission, independent review acceptance or protected Root/Parent authority.

Standalone non-dry-run `implement` admission rejects a selected Linux worker
extent below 64 bytes or above the shared 296,885,960-byte inclusive maximum before image hashing,
composition, or durable store/owner effects. Existing read-only retained-history
and namespace checks keep their earlier priority. Every production-batch node is
checked during the common selected-input preflight, before any plan import,
batch marker, durable selected intent or node dispatch. Shared composition and
non-dispatch `quality-baseline`, `pr` and `merge` do not apply this worker extent
policy. Dry-run inspection does not admit a worker or enforce its dispatch size.
This is refusal-only DATA admission, not ELF validity, conformance or authority;
the in-port read reservation and actual same-owner image/scope proof remain
mandatory. The fixed message identifies an INCOMPLETE capability; the existing
standalone failure wire remains ERROR, not a new outcome mapping. The measured
296,885,960-byte official Linux Codex image is extent-eligible under the approved
byte profile. This does not establish that the actual CLI executes successfully
from a memfd, is authenticated, or has installed conformance. An in-range extent
enables no protected Linux runtime policy or independent-review acceptance.

The child copies the selected executable into a sealed executable memfd. The
original parent independently verifies the same descriptor, its kernel identity,
complete bytes and seals before RELEASE. The child executes that descriptor with
`execveat`; there is no script or pathname fallback.

Ordinary scopes that never enter exact-image binding retain their original
14,680,064-byte WORK and 16,777,216-byte total kernel read ceilings. Actual
exact-image admission checks image plus EOF against the approved absolute
300,031,689-byte WORK ceiling. On that same counter it captures a per-instance
WORK ceiling equal to prior debits plus selected image plus EOF plus 3 MiB,
capped at 300,031,689 bytes. Its total ceiling adds 2 MiB for cleanup, capped at
302,128,841 bytes. Thus a smaller image has at most 3 MiB of later WORK metadata
headroom, not the maximum image's unused extent. At the inclusive maximum of
296,885,960 bytes, prior metadata reduces that later headroom. ALL prior metadata
debits stay on the same counter; no bytes or time are refunded or reset.
Insufficient remaining WORK credit refuses before descriptor open. The shared
public maximum is profile DATA, not native authority. The child gate's existing
512 MiB ceiling is unchanged and grants no additional parent allowance.

ALL Linux Tool originals now have a 2,147,483,648-byte cumulative complete-read
ceiling; Windows and other platforms retain 1,073,741,824 bytes. Both read debit
and capacity admission consult the same platform ceiling on the existing
per-original counter. The shared 4,096-operation and 268,435,456-byte write
ceilings are unchanged. Read's default per-file maximum remains 16 MiB and its
maximum allowed argument remains 256 MiB; native hashes stream with 64 KiB
buffers under the separate existing 512 MiB native-file extent ceiling.

Root admission plus an ordinary Linux Codex worker accounts four complete image
passes: root pathname hash, worker pathname hash, gate copy and parent sealed-fd
hash. The last two reserve 2*(image bytes+1) before birth. The selected measured
image therefore debits 1,187,543,844 bytes and five operations before nonimage
inputs. Actual selected inputs and remaining credit must still fit; this is no
universal pipeline or batch-fit guarantee. No new quality-receipt count limit is
introduced. Native memfd writes and private operator fixture/provisioning writes
are separate explicitly bounded domains, not Tool WriteNew credit. For the
default/null policy, source cache, memfd, loader and descendants share the 4 GiB
scope memory cap. For the selected restrictive exact child, the same components
share its total 2 GiB cap, including the 296,885,960-byte memfd and its page cache.
Non-helper Linux fixtures, including STOP, refuse an ambient root helper or
ancestor drop-in; they require the separately selected rollback first.

The measured official Linux Claude Code 2.1.306 image is 290,532,720 bytes,
SHA-256 `520bc6c1f40af466bd03a278b5ae1af1a2938bc7de5b9e5cb15526da20d71cfe`.
Its complete signed-release download was verified; this does not establish
protected review compatibility. Independent review requires twelve complete
image passes per reviewer image. Together with the four measured Codex passes,
that is 4,673,936,496 bytes before nonimage inputs, exceeding the 2,147,483,648-byte
Linux original read ceiling. Protected Linux review remains fail-closed under
the existing production guards. This change enables no RuntimeTrust platform
branch, auth copy, model/provider change or reviewer policy.

The hash loop keeps one bounded read record with a finite syscall count and
actual return facts for each read. A short-read plan refusal, deadline or failed
hash does not create a successful image proof. Original open, identity, seal,
first-close and cleanup records remain independently required. Once exact-image
binding has entered, WORK admissions stop at 8,192 retained syscall rows; cleanup
can use the remainder of the SAME 16,384-row ceiling. The exact-image hash frame
uses that WORK admission limit as well. Ordinary scopes that never enter exact-image
binding retain the original 16,384-row WORK ceiling; cleanup shares the remaining
rows of that same counter. No row counter is reset when exact-image binding enters.
Long exact-image work can still exceed its finite partition and must refuse.
These partitions preserve cleanup headroom, not a guarantee that an unknown native
effect will settle or that cleanup is permitted after its original clock expires.
An exact-image descriptor whose first-close WORK admission fails can continue
that first close in SAME original cleanup only while the native close invocation
has not entered. The close-attempt marker remains set; a separate invocation fact
is set inside the retained syscall callback immediately before `close`. WORK or
row admission refusal before that callback creates no native close to retry.
Failure cleanup is first notified to the same enclosing owner, so a subordinate
WORK view cannot silently prevent its actual failure disposition. Once the native
close invocation enters, it is never retried, including failed returns or posts.
If cleanup admission or native closure remains unknown, the descriptor stays
retained and cannot count as disposed. Admission, close and post failures remain
retained. No rows, bytes or time are refunded or added.

For default/null selection, all memfd pages, source page cache, loader/runtime pages and descendants consume
the same scope `MemoryMax=4294967296` and `MemorySwapMax=0`. This is a total scope
cap; it does not promise 4 GiB of target heap in addition to the sealed image.
CPU, memory, time, tokens, call-row and cleanup-duration limits are unchanged.
Only the explicitly described image/kernel and Linux managed read-byte ceilings
are increased; no additional original or resource owner is created.

A new ordinary Linux gate build and package are required. The selected build
audit must enumerate every actual compiler source, including `ExactNativeImage.cs`,
and join its PDB source checksums to the five selected gate outputs. Old receipts
must remain preserved and cannot certify rebuilt bytes.

Genuine guest controls must establish descriptor execution, shared memory
charging, successful retirement and precise hash/extent/ELF refusal. Kernel seal
controls alone do not establish the process-owner binding. Replacing a pathname
after RELEASE does not establish a pre-RELEASE race witness. Mid-copy cancellation,
pre-RELEASE replacement and forged descriptor/READY controls remain separate
acceptance requirements before broader protected-runtime certification.

## Proposed explicit helper dependency policy

The optional `nnp-user1000-ancestor-v3` exact-image child policy is restrictive DATA
selection, not a Root or runtime certificate. The source-attested birth gate sets
`PR_SET_NO_NEW_PRIVS` on its main-thread leader before READY and retains it at
exec. Before RELEASE, the existing creator-bound owner reads that actual PID's
complete bounded procfs status and requires NoNewPrivs=1, all four UID/GID fields
1000, and zero inheritable, permitted, effective and ambient capabilities. It
retains the same original counters, generation checks and first-close semantics.
Ordinary captures (including prerequisite Git/plan import using the SAME selected
profile) keep their ordinary launch/NNP behavior. The recognized policy adds the
ancestor-resource check to those captures. Its NNP token/status requirement applies
only when an exact image is selected; ordinary capture is not rejected.
Default/null policy is unchanged. Helper admission is explicitly opt-in fixture
DATA; existing exact-version STOP/malformed/other fixtures are not auto-selected.

A conformance fixture may explicitly select the measured official
`/codex-code-mode-host` (74277776 bytes, SHA256
`6b4de7a1a69656779c88b6e249ab976cbbc9a43e1edf65e6ec9927feb26f996b`)
as a root-owned 0555 path dependency after a separate owner decision, actual
provision receipt, fresh boot, no-follow metadata, a prebirth full original-credit
hash and a second same-original full postrun hash. The primary stays sealed; this child is not sealed or a protected Linux
reviewer. Root/operator mutation and privileged brokers remain trusted: NNP
prevents exec privilege gain, not privileged IPC or compromise of other trusted
processes. The operator installer must be closed before model entry. No global
host sudo/auth/service/model policy or numeric product allowance is expanded. Missing policy,
proof, credit or helper refuses; protected Linux RuntimeTrust remains closed.

The explicit offline Route A proposal additionally installs a Root-owned
user-1000.slice resource drop-in. This is a guest service-policy exception needing
new owner approval. Selected-profile owners observe the actual root-controlled
ancestor cgroup and exact effective CPU/memory/swap/task ceilings; all forge user
manager units share those ceilings. Status also requires supplementary Groups1000.
The profile does not claim a complete sandbox or universal original-group closure.
Only a separate Root audit after the original whole-VM shutdown may accept the
unprotected conformance scope; protected Linux RuntimeTrust stays closed.

V7 offline provisioning is paired with one separately approved read-only installed
receipt-inspection boot. That boot can activate a partial ancestor policy before
inspection; it is not a model/profile admission. Missing/failed/extra receipt
entries, a changed helper/drop-in, SSH failure, or unknown VM closure blocks the
profile. The fixture reads the raw completed receipt directly, checks its nonce,
root UUID, inner helper tuple and policy digest, and captures installed-boot device
identity rather than assuming rescue major/minor numbering is portable. Existing
post-retirement owned Git observation checks the same ancestor; policy metadata
and full88-byte digest are checked before and after on the same original.

The owner packet also contains a separately selected offline rollback program. It
only unlinks the exact two newly published helper/policy hardlinks after joining
the retained root-private stage and prepared receipt; all stage/attempt evidence
and directories remain. Every rollback original pays its own full rescue-media
hash. Rollback is not automatic, a retry, arbitrary cleanup, or authority adoption.

### Proposed V8 closed child and final disposition

The opt-in nnp-user1000-ancestor-v3 child is stricter: 48 tasks and 2 GiB under the unchanged root-controlled ancestor/global 128 tasks, 4 GiB and two CPUs. Ordinary null selection retains its prior limits. The arithmetic difference is not measured free capacity, a reservation or a guarantee against hostile same-UID manager brokerage; actual Codex/helper fit remains unproved. Only COMPLETE may select the root-owned helper; STOP cannot. No protected runtime authority is issued.

Before any offline archive/ISO or persistent write, bind the actual current source/Csc/PDB and gate-five-file build acceptance. The existing already-running KVP daemon supplies fresh nonce READY, one host ACK before installed-root RW, and FINAL only after installed-root unmount/clean plus seed unmount. The host retains FINAL before first ID-only graceful shutdown. Missing/failed/unknown FINAL blocks profile even if completed.json exists. No new service, transport or credential route is implied. Fresh same-running-boot guest preparation stages approved decision/final DATA at actual guest paths and derives PreparedBootId there; inspection's previous boot ID and Windows paths are inadmissible. All byte exceptions and persistent policy remain owner-pending.

V9 private correction: only the opted-in exact native image receives the lower
48-task/2GiB child limits; ordinary prerequisite captures launch and read back
their original128-task/4GiB scope. New operator permission must explicitly cover
one host VM-configuration AddKvpItems and conditional RemoveKvpItems. The fresh
ACK is removed once only after raw matching FINAL is retained while the VM is still Running; after Off, only read-only original-frame verification is permitted;
original indexed HostExchangeItems bytes must match exactly afterward. Foreign
values stay opaque and are not exported. A failed/missing FINAL, unknown Add or
Remove job, or changed host frame blocks acceptance and preserves uncertainty.
Existing daemon refresh latency and actual guest fit remain unproved.

For the optional restrictive policy, the actual owner must be outside
`/user.slice/user-1000.slice` and its descendants. Before loading the library,
opening the bus or creating the birth root, the parent reads its own complete
unified-cgroup membership under the original bounded 8 KiB read and refuses an
in-ancestor, malformed or unknown membership. The default/null policy is unchanged.
This check establishes a refusal boundary, not owner placement. The current
prepared operator does not provide the required privileged outside-ancestor owner
launch; that remains a concrete owner-policy and implementation dependency.
No separate CPU, memory or process domains are summed into a claimed global
128-task guarantee. This proposal changes no resource limit, service, account,
authentication or VM configuration.
